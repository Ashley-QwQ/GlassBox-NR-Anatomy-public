# Beginner Glossary: Look Up When Needed, No Need to Memorize First

[Entry Story](INDEX.md) · [One Block](L1_00_one_block_primer.md) · [History](L1_00_history_primer.md) · [Number Points and Small Baskets](L1_00_numbers_primer.md)

The 111 groups follow the order of the beginner review. A term may be used for images, arithmetic, execution, or verification; in particular, build codenames, storage formats, and verification statuses are not additional network layers. Basic meanings are given here; see the main text for exact contracts.

## Images, Inputs, and Structure

| Term or notation | How to understand it on first encounter |
|---|---|
| <a id="g001"></a>native behavior, target binary | Native behavior is the computation actually exhibited by the observed program; the target binary is the program file with locked version and content identity. Explanations from reading CPU source code cannot automatically be called observations of it. |
| <a id="g002"></a>state, processed state, temporal state | Numbers saved for later steps or the next frame. In this route, the color state id9/id6, internal features, and the full workspace are distinct objects and cannot be merged under the single word "state". |
| <a id="g003"></a>color base, display base | A backup copy of the current frame's original color, used for display blending at the tail end; not another hidden feature. |
| <a id="g004"></a>intensity | The strength for blending the processed color with the current-frame backup in the display stage; it is not the B70 history blending share. |
| <a id="g005"></a>style, tone, structure | Three named control values that affect numeric values after being fed into conditioning channels; the full visible effect caused by each is undetermined, and a training objective cannot be supplied from their English names. |
| <a id="g006"></a>automask, skin, mask, skin-mask | Mask- or skin-related names in this project's control/capture labels; the two explained p5 masks are scalar conditions, not per-pixel mask images read separately here. The names do not prove what effect they have on which image regions. |
| <a id="g007"></a>channel, 16→32, 512/1024 channels | The channel count is the number of numeric items saved at one position; 16→32 combines 16 items into 32 items—it is not 16 frames turning into 32 frames, nor does it directly change image width or height. |
| <a id="g008"></a>feature | Numbers computed and passed inside the network. Knowing there are 32 items does not mean knowing which item specifically represents edges, skin, or detail. |
| <a id="g009"></a>encoder/encoding, decoder/decoding | Here this refers to the stages where the first half progressively reduces grid density and the second half progressively restores density; not the forward and inverse operations of file encoding. For "decoding" of numeric codes, see Q8/D8. |
| <a id="g010"></a>global bottleneck | A deeper section of the network with fewer positions, where positions can interact globally; "bottleneck" here is not proof that it is the slowest part. |
| <a id="g011"></a>TIN | The family label for a set of window blocks and storage layouts in this skewer; actual operations are explained on the window page, and the architecture is not inferred from the three letters. |
| <a id="g012"></a>Swin, Transformer | A Transformer typically exchanges content across positions using attention and transforms channels using per-position computation; Swin is a model name associated with windows and shifted windows. The names here are used for comparison or identification and do not prove that a standard structure was copied verbatim. |
| <a id="g013"></a>split16, 16 heads | The family name for the 512-item window blocks in this skewer; numbers used for comparison are split into 16 heads of 32 items each. The eight FFN groups and device execution groupings are separate axes. |
| <a id="g014"></a>ViT | A common name for applying a Transformer to image positions; in this skewer it specifically refers to the section with 1024 items, 32 heads, and eight global blocks, and a standard implementation cannot be supplied from the abbreviation. |
| <a id="g015"></a>window, 8×8 window, shifted window | Allows only a group of neighboring positions to exchange content in a given attention step; 8×8 is 64 positions. Changing the starting origin of the window partition in the next block lets positions contact a different set of neighbors; it does not shift the final image. |
| <a id="g016"></a>skip, bypass | Earlier numbers are saved, bypass some intermediate steps, and are fed back in later. What is saved is internal numbers, not necessarily a visible image. |
| <a id="g017"></a>residual | Numbers inside a block that bypass a sub-stage and reconnect; in this skewer they are often multiplied by a scale first and added as the starting subtotal of a matrix. They must not be conflated with cross-stage skips or display blending into a single end-of-block plus sign. |
| <a id="g018"></a>full, pool, pooled, pooling | full is the fuller-density exit at a given tier, and pool/pooled are role names for the sparser exit. Pooling generally refers to merging neighborhood information; the name itself does not dictate an averaging formula, and question marks remain where spatial correspondence is undetermined. |
| <a id="g019"></a>repack, rearrangement, swizzle | Changing the storage order of the same numbers or bit patterns. Example: changing (a,b,c,d) from two rows of two slots to one row of four slots; swizzle here refers to address-bit permutation, not an extra content transformation. |
| <a id="g020"></a>interpolation, convolution, closed form, induction | Interpolation estimates other positions from existing ones; convolution combines a neighborhood using a set of coefficients. Closed form means an explicit rule that does not rely on item-by-item lookup in a prebuilt index table; induction summarizes a pattern from named samples and does not yet prove it for all inputs. |
| <a id="g021"></a>upsampling, downsampling, nearest-neighbor | Increasing or decreasing internal grid positions; nearest-neighbor copies the numbers from a selected nearby position. Different stages in this skewer use different arithmetic, and one cannot conclude from this that the final display resolution changes. |
| <a id="g022"></a>outview, inpview, chained | Family names for output-view interface, input-view interface, and consecutive same-tier blocks; launches with these names may still perform full numeric computation rather than merely swapping containers. |
| <a id="g023"></a>motion vector, MV | Two numbers per position in this route that participate in the coordinate formula for "where to sample from the previous image". Their general host direction and units are undetermined and must be read together with their scales and transforms. |
| <a id="g024"></a>temporal, history, carry | Temporal involves preceding and succeeding frames; history is the old state permitted to be read; carry is saving and continuing one's own state, not a new operator layer. |
| <a id="g025"></a>reprojection, temporal sampling | Computing a sampling position in the old image from the current position and motion numbers, then filtering to fetch color. B0 and B70 each have their own transforms and do not share a single sampling result. |
| <a id="g026"></a>alpha, fourth channel | The fourth stored component of an image, commonly used for opacity/coverage in image processing. This route does not use it as a network color input, and the result image writes a fixed 1; the fourth predicted value separately participates in the history share and cannot be equated with alpha. |
| <a id="g027"></a>texture, texel, TEX | A texture is a numeric image that can be sampled by coordinates; a texel is one cell in it. In the main text, TEX denotes one sampling operation with specified filtering rules, which does not necessarily read only a single cell. |
| <a id="g028"></a>RGBA16F, RG16F | Storing R/G/B/fourth item per position, or storing only two items; each item uses F16. They are storage representations, not two new network layers. |
| <a id="g029"></a>tap, 5-tap, 4-neighborhood, bilinear, sidelobe | A tap is one filtered sampling point; each point of a 5-tap filter can itself be filtered from a 4-neighborhood. Bilinear combines four corners by distances along two axes; sidelobes are contributions outside the center—in this skewer the outer layer can be negative, while the inner layer has its own precision rules. |
| <a id="g030"></a>mirroring, reflection, boundary sampling | Reflecting out-of-bounds image coordinates back inside the edge according to a rule. For example, y=1080 beyond 1080 rows in this instance reflects to 1078, rather than stretching the whole image. "Mirror" in the sense of a source-code copy is a different meaning. |
| <a id="g031"></a>gain, scale, scaling | Multiplying numbers by a factor to scale them up or down overall; input color scale, bypass scale, query scale, and display intensity are distinct quantities, not the same knob. |
| <a id="g032"></a>p5, reset, parameter branch | p5 is the label for a conditional control branch; under the recorded contract, reset does not consume old history and overwrites it with the new state at the end of the frame. Branching depends on multiple parameter/resource conditions and cannot be triggered by changing the counter alone. |
| <a id="g033"></a>HSL, h/s/l, hue, saturation, lightness-like quantity | Hue indicates color category such as red or green; saturation indicates distance from gray; the lightness-like quantity is constructed from color maximum and minimum values, not physical illuminance. This skewer uses HSL-like decomposition/recomposition with a specific channel order; the exact formulas remain the authority. |
| <a id="g034"></a>Oklab, LMS | Two names related to color coordinates: Oklab aims for approximate perceptual uniformity, and LMS relates to the three cone responses. They are legacy naming references and do not replace the current HSL-like formulas here. |

## Comparing Positions and Processing Channels

| Term or notation | How to understand it on first encounter |
|---|---|
| <a id="g035"></a>operator | A well-defined processing step, such as summation, format conversion, or coordinate-based fetching; not every operator corresponds to a single device launch. |
| <a id="g036"></a>logical block, B number | Dividing the network wiring into functional blocks, numbered B0 through B70; a single block may span multiple execution launches. |
| <a id="g037"></a>FFN, ffwd, ffwd_proj, feed-forward | The sub-stage in a block that first processes each position's channel vector independently; ffwd and ffwd_proj are concrete family entry points that may split this sub-stage across separate executions. Content is not yet exchanged across positions here. |
| <a id="g038"></a>projection, proj, post-projection | Recombining an input number sequence into another sequence using coefficients; not specifically 3D camera projection. Post-projection combines attention content back into block channels. |
| <a id="g039"></a>attention | The current position scores candidate positions and uses positive shares to combine the content of those positions; read the [three-position story](L1_00_one_block_primer.md#qkv-story). |
| <a id="g040"></a>Q/K/V, query/key/value | Q is used to ask from the current position, K is used to be compared against, and V is used to retrieve content; all three are computed from internal numbers, and scores do not score V itself. |
| <a id="g041"></a>token | A participating position and its vector of numbers; a position in a deep grid does not necessarily correspond to a single pixel of the original image. |
| <a id="g042"></a>seed | The subtotal brought in at the start of an accumulation, which may be zero, a previous subtotal, or a bypass value; here it is not a seed for random number generation. |
| <a id="g043"></a>normalization, norm, norm32, vector norm | Adjusting the overall magnitude of a group of numbers; a vector norm is a kind of "length". In this skewer, each 32-item Q/K group sums squares, takes a specified reciprocal square root, and multiplies item by item; V skips this step, and no mean is subtracted. |
| <a id="g044"></a>LayerNorm, mean, variance | The mean is the average, and variance is the average squared deviation from the mean; standard LayerNorm centers first and then normalizes by scale. The Q/K sum-of-squares scaling in this skewer is not that block-entry operation. |
| <a id="g045"></a>G, gate function, activation | Each input number is modified by a single-input function; here G is a clamped piecewise polynomial followed by format conversion. "Gate" does not mean a binary on/off switch, nor is it an acceptance gate used for verification. |
| <a id="g046"></a>GELU, SiLU, SwiGLU | Names of other activations/gates: GELU scales the input by a smooth cumulative distribution, SiLU multiplies the input by a smooth S-shaped function, and SwiGLU multiplies two independent projections elementwise. They are reference comparisons and cannot replace G in this skewer. |
| <a id="g047"></a>softmax, exp, row maximum | Standard softmax takes the natural exponential exp across a row of scores and divides by the total; the row maximum may be subtracted first to control intermediate magnitude. The encoded positive weights here follow a different formula and cannot be treated as identical just because both produce shares. |
| <a id="g048"></a>φ, positive kernel, weight w / share p, Den | φ turns scores into positive numbers, w is the unnormalized weight before dividing by the total, p is the share after division, and Den is the total denominator. "Kernel" in "positive kernel" means a mathematical function transform, not an execution kernel; after rounding, p does not necessarily sum to exactly 1. |
| <a id="g049"></a>affine, clamp/clip, Sat01, clamping | Affine here means multiplying by a constant and adding a constant; clamping pulls out-of-range numbers back to the nearest endpoint. Sat01 clamps to 0 through 1 and must not be confused with E4 finite saturation. |
| <a id="g050"></a>reduction, denominator tree, partial sums / Partials | Combining multiple terms into fewer terms according to specified pairings; intermediate subtotals stored along the way are called partial sums. Under finite precision, (a+b)+c is not necessarily equal to a+(b+c), so the tree structure and order matter. |
| <a id="g051"></a>M×K×N, matrix, dot product, dense, BLAS/GEMM | A matrix is a table of numbers; multiplying corresponding items of a row and a column and adding them up is a dot product. Multiplying M rows of K items by K rows of N items yields M×N; dense denotes dense connectivity or storage context, and BLAS/GEMM are standard linear-algebra interfaces / matrix-multiply routines that do not carry this skewer's rounding contract. |
| <a id="g052"></a>position bias / bias, query scale, confidence scale / confidence, sigmoid/logistic | Position bias adds a specified term to the score for a pair of positions; query scale multiplies Q; confidence scale limits history blending. sigmoid/logistic are names for functions that map numbers to an S-shaped share between 0 and 1; the share does not thereby become a calibrated probability. |
| <a id="g053"></a>RMS, L2 unit vector, ε, β | RMS is the square root of the mean of squares; an L2 unit vector scales length to 1 by dividing by the square root of the sum of squares. In this skewer, ε acts as a lower bound on the sum of squares rather than being added; β often denotes an additive offset, and there is no β addition after this scaling in this skewer. |

## Finite Numbers and Rounding

| Term or notation | How to understand it on first encounter |
|---|---|
| <a id="g054"></a>F16, half, binary16 | The same 16-bit floating-point format, which can only store specific number points—not 16 digits of decimal precision. Read the [number-line primer](L1_00_numbers_primer.md) first. |
| <a id="g055"></a>E4, E4M3, FP8 | A one-byte floating-point code in this skewer with 1 sign bit, 4 exponent bits, and 3 mantissa bits; it has fewer representable points than F16 and is not an extra set of colors. When E4 is used as a historical capture codename, see the workstream glossary entry. |
| <a id="g056"></a>F32, binary32, binary64, double precision, floating-point | 32-bit and 64-bit floating-point numbers; they store a significand scaled by a power of two and still have finite precision. Using 64-bit intermediates in the CPU reference does not prove that the device uses 64-bit internally. |
| <a id="g057"></a>f32/u32/u64, U32, raw32, bits16, bit pattern | f32 interprets 32 bits as floating-point, while u32/u64 interpret bits as unsigned integers; raw32/bits16 emphasize raw bit strings. The bit string 0x3e00 decodes as 1.5 in half precision; the encoded integer and the numeric value are not the same thing. |
| <a id="g058"></a>exponent, mantissa, field exponent, unbiased exponent, significand | Like 6 = 1.5 × 2², where 1.5 is the significand and 2 is the scaling exponent. The exponent field stored in the encoding carries a bias and special rules and does not necessarily equal the number's unbiased exponent; common-grid scale selection must distinguish between them. |
| <a id="g059"></a>RN-even, RN16/RN32/RN64, RNE16, half_round | Find the nearest representable number, and only on an exact halfway tie choose the one whose significand has least significant bit 0; the number after RN is the target format bit width, and half_round is the implementation function name. |
| <a id="g060"></a>RZ, RZ16, trunc, round toward zero | When discarding parts beyond target precision, move toward zero: positive numbers become smaller and negative numbers become less negative. trunc is a common name for truncating the fractional part; it must not be confused with floor rounding on negative numbers. |
| <a id="g061"></a>Q8/D8, quantization/decoding | Q8 maps F16 to the coarser E4 code, which may lose information; D8 expands that code exactly into F16 and cannot recover information lost earlier. |
| <a id="g062"></a>satfinite, finite saturation | When a value exceeds the finite endpoints of the target format, clamp it to the maximum finite magnitude; this is not clamping to [0,1], nor does it cancel a rejection from a preceding operation. |
| <a id="g063"></a>H+, H×, HF, h_fma, fused multiply-add / FMA | Half addition and multiplication each round and store their result; fused multiply-add keeps the product from being rounded separately before the specified addition. The software reference preserves the boundary of fusing in binary64 and then rounding to half, which cannot be described as a universal internal hardware structure. |
| <a id="g064"></a>accumulator, partial sum, subtotal feedback | Stores the current subtotal to be fed into the next accumulation step. It has already been affected by prior rounding and is not a bag that holds the mathematically exact sum indefinitely. |
| <a id="g065"></a>K16, K32, Q32, QMMA, HMMA | Shorthand in this document for 16-term and 32-term matrix accumulation steps and hardware primitive families; the numbers are not thread counts or window sizes. Input formats, grid truncation, and evidence are bound separately for the two families. |
| <a id="g066"></a>common grid points, alignment exponent, grid step, field F25 | Within a basket, products and the subtotal are first placed onto the same power-of-two scale; the alignment exponent determines the grid step. field F25 is the name of the scale-selection rule for this target candidate (see L4 for the exact formula) and does not mean storing into a new F25 format. |
| <a id="g067"></a>value/renorm candidates | Alternative arithmetic hypotheses for choosing the common scale—such as using the numeric value exponent or a renormalized exponent; they are candidate rules to be discriminated, not two network layers. Exact differences follow the candidate table. |
| <a id="g068"></a>normal/subnormal, FTZ, tiny, DAZ, gradual underflow | Subnormals are smaller representable points near zero in a format; gradual underflow continues using those points, FTZ flushes tiny inputs or outputs to zero at specific sites, and DAZ specifically treats subnormal inputs as zero. tiny merely refers to tiny-magnitude contexts; rules must be checked per operation. |
| <a id="g069"></a>Inf, NaN, nonfinite, NaN payload / quiet NaN | Inf denotes infinity and NaN denotes not-a-number, neither of which is an ordinary finite number; the payload is the bits preserved in a NaN encoding, and quiet is one class flag of NaN. Current interfaces may reject them, so they cannot be casually treated as zero. |
| <a id="g070"></a>+0/−0, signed zero | Two zero encodings that compare equal numerically; byte comparison distinguishes them, and certain operations preserve the sign. Numeric equality cannot substitute for bitwise equality. |
| <a id="g071"></a>overflow, underflow, cancellation, dynamic range | Overflow is when magnitude exceeds the format's range; underflow involves tiny results; cancellation is when positive and negative terms cancel out; dynamic range describes the span of large and small magnitudes handled together. Whether the implementation rejects is a separate decision. |
| <a id="g072"></a>RSQ/RCP, EX2/LG2 | Indicate the purposes of 1/√x, 1/x, 2^x, and base-2 logarithm respectively; what this project requires is the exact output bit pattern of the certified function, not an arbitrary math-library approximation. |
| <a id="g073"></a>MUFU, SFU, SQRT, SIN/COS, Radius | The first two are names for special-function units or primitives; the latter are square root, trigonometric functions, and combined radius. In this skewer, Radius already includes multi-step composition rather than taking a direct square root of k. |
| <a id="g074"></a>libm, function wrapper, certified function map / function table, Domain | libm is the standard math library; a function table stores the exact output code for each specified input code. A wrapper checks the domain, transforms codes, or rounds on the outside; Domain is the set of permitted inputs. Finding an entry in a table does not bypass caller restrictions. |
| <a id="g075"></a>integer hash / Hash32, Box–Muller, RNG, xor, U32 wraparound | A hash mixes position and counter into a deterministic integer; xor is bitwise exclusive OR; U32 overflow wraps modulo 2³². RNG generally refers to a random number generator, and Box–Muller is a common method for constructing zero-centered perturbations from uniform numbers; this skewer recomputes from fixed coordinates and counter with no per-pixel recurrent state. |
| <a id="g076"></a>scalar, vector, tensor, axis | A single number, a 1D sequence of numbers, and a multidimensional table of numbers; an axis is one dimension of the table. Logical spatial/channel axes and device work-assignment axes must not be treated as the same axis just because they have the same length. |
| <a id="g077"></a>MAC/GMAC, QK, AV, bandwidth | MAC counts one scalar multiply-add and GMAC counts one billion; QK is score comparison and AV is content combination by shares. Bandwidth is the amount of data moved per unit time; an operation-count table is not itself a bandwidth or speed measurement. |

## Program Execution and Storage

| Term or notation | How to understand it on first encounter |
|---|---|
| <a id="g078"></a>DLL, GPU, SM, sm_120, architecture, shader | A DLL is a program library file; the GPU executes parallel tasks, SM is one of its compute-unit organizations, and sm_120 locks the target architecture; shader is a common name for a device program. They describe the execution target, not feature channels. |
| <a id="g079"></a>weights, WEIGHTS_HT, resource, weight container | Weights are coefficients that multiply inputs or act as scales/biases during computation, and a resource/container is the carrier that stores them; WEIGHTS_HT is the resource name in this object and does not represent a network operation. |
| <a id="g080"></a>kernel, launch, family, fused kernel | A kernel is a device compute program, and a launch is a single request to execute it; a family groups similar entry points, and a fused kernel packs multiple computations into a single launch. Operator counts, block counts, and launch counts are counted separately. |
| <a id="g081"></a>L0/L1 reading levels vs. launch L0–L157 | Reading levels indicate document depth; launch L0–L157 indicates default execution indices; B numbers indicate logical blocks. Headings list all three together; do not mistake an L2 page for the second layer of the network. |
| <a id="g082"></a>workspace, WS | A large contiguous memory region holding intermediate numbers, handoff buffers, and management flags; retaining it does not prove that every old byte is required cross-frame memory. |
| <a id="g083"></a>params, CB, constant buffer, byte offset | A packet of configuration received by each launch, containing dimensions, pointers/handles, control numbers, and so on; CB+0x40 is a hexadecimal byte offset within that packet, and the value read from it is a different concept from the 1/256 subpixel grid of the sampling algorithm. |
| <a id="g084"></a>role, pitch / row stride, Span / base address | A role names a segment of storage at a given point; the base address is the starting point, and Span is its byte interval. pitch is the byte distance between the starts of adjacent rows, which may be longer than the valid pixel row. |
| <a id="g085"></a>logical/physical, T/P, extent, padding | Logical refers to position/channel meaning, while physical refers to actual memory layout; extent is the declared dimension. T is the valid position count, and P includes padded rows. Extra cells are sometimes genuinely written and read and cannot be discarded across the board; final display is still cropped to the input dimensions. |
| <a id="g086"></a>batch=1 | Processing one sample at a time; the omitted batch axis has length 1, rather than feeding all frames of a video in together. |
| <a id="g087"></a>thread, warp, lane, CTA, grid, tile, shared / shared memory | A thread is one unit of work executing a device program; this target groups 32 threads into a warp, and lane is the 0..31 index within that warp. A CTA is a cooperative thread block containing several warps, and a grid is the set of CTAs in one launch; a tile is a data/work partition, and shared is temporary storage shared within a cooperative block. These work groupings do not automatically equal image positions, channels, or attention heads. |
| <a id="g088"></a>descriptor, inputlayout/outputlayout, HWC/CHW, planar split | A descriptor records a resource's dimensions, format, and metadata; layout specifies storage order. HWC orders position before channel, CHW orders channel before position; planar split stores certain channel groups in separate planes. The numeric meaning can be the same while byte addresses differ. |
| <a id="g089"></a>mapexec, scalar_map, maps, wiring, DAG, provenance graph | maps specify "where to fetch from and where to write to", while wiring/DAG specify "which results are computed under what dependencies"; a DAG is a directed acyclic dependency graph. Evaluating the graph in an executor does not prove the graph has been reduced to a spatial closed form. |
| <a id="g090"></a>sread/xsite/wload/gstore, A_src/B_off, OUTMAP/REDMAP | Names of concrete source/output tables: shared-memory read, cross-site source, weight load, and global output store; A_src/B_off select matrix inputs and weights, while OUTMAP/REDMAP select final output and reduction sources. They are not network layers in the beginner diagram. |
| <a id="g091"></a>release/publication, completion flag, wait, synchronization | Publication/release may mean storing a numeric value at a rounding boundary or writing a "ready/completed" management slot; wait/synchronization constrains task ordering. CPU return order does not automatically prove the full concurrent timing on the device. |
| <a id="g092"></a>aliasing, lifetime, asynchronous, epoch | When two names refer to the same or overlapping storage, it is called aliasing; lifetime refers to when storage is valid; asynchronous execution allows proceeding before a task finishes; an epoch is one stage or round of an execution graph and does not automatically equal a video frame number. |
| <a id="g093"></a>WriteSet/CumWrites, readset, WR A/B, complement | Single-launch and cumulative declared write ranges, and actual read range; the complement is outside that range. WR A/B respectively check stability of self-reported ranges, coverage of native changed bytes, and invariance of CPU bytes outside the range; all are verification objects, not network layers. |
| <a id="g094"></a>ownership, unique writeback, exact-once, side effect, typed zero-write | Constraints such as who owns writes to a memory region and writing each destination location exactly once. Side effects include extra writes such as completion slots; a typed zero-write additionally specifies width, value, and timing. Two tasks colliding on the same cell make "which write survives last" ambiguous, so one cannot merely count output length. |
| <a id="g095"></a>atomic add, same-address contribution, parallel scheduling | Multiple tasks accumulating into the same cell; an atomic operation prevents a single read-modify-write from being interleaved by another task, but does not automatically fix which task arrives first. Under finite precision, arrival order can still change the result. |
| <a id="g096"></a>caller, host, API, handle, surface, ABI | The caller/host is the external party providing inputs and controls; the API is the call interface, a handle identifies a resource, and a surface is a writable image resource interface; the ABI specifies parameter byte layouts and calling conventions. Knowing these meanings does not mean the host-side generation branch has been reconstructed. |
| <a id="g097"></a>little-endian / LE, NPZ/NPY, payload, codec, zigzag | Little-endian stores the low-order byte of an integer first; NPY stores an array and NPZ packages multiple arrays; payload is the actual data content; codec is the encoding/decoding method; zigzag maps small signed integers to nonnegative integers convenient for storage. These belong to storage representation. |
| <a id="g098"></a>TwoSum, strict floating-point compilation, fast-math, implicit contraction, FE_TONEAREST | TwoSum stores the sum and exact rounding error of an addition in high and low parts; strict compilation prevents the toolchain from reordering or altering evaluation. fast-math permits certain algebraic rewrites, implicit contraction may fuse multiply and add into FMA, and FE_TONEAREST is the round-to-nearest-even floating-point environment; none of these is a network layer. |
| <a id="g099"></a>runtime, checkout, mirror, asset loading | runtime is the execution-wiring code, checkout is a working copy of source code, and mirror can also refer to a content copy; loading reads the required data into memory. Distinct from image boundary reflection, a copy path does not equal content identity. |

## Evidence and Historical Codenames

| Term or notation | How to understand it on first encounter |
|---|---|
| <a id="g100"></a>CPU reconstruction, verification record, CENSUS/MEASURED/CONTROLLED/INFERRED | CPU rules are a reproduction hypothesis; CENSUS is source reading / inventory, MEASURED is named measurement, CONTROLLED is controlled comparison, and INFERRED is inference. Example: "the source code sums first" is CENSUS; "output bytes match on a given input" is MEASURED; "changing only the summation order causes a difference" is CONTROLLED; internal motivation may still be only INFERRED. |
| <a id="g101"></a>admission, rejection guard, acceptance domain, contract | The implementation promises to compute only under a given set of conditions; a guard checks those conditions and rejects on violation, producing no output that can be counted as a match. A contract specifies the object, inputs, operations, and boundaries together. |
| <a id="g102"></a>gate, full-chain gate, single-launch gate, negative/positive control | In a verification context, "gate" means a scoped acceptance check; full-chain and single-launch gates have different scopes. A positive control checks a condition that should pass, while a negative control deliberately alters a critical condition and should be rejected or produce a difference; obtaining a difference on a negative control does not mean the main result failed. |
| <a id="g103"></a>binding, frozen, seal, build, SHA/identity | Binding specifies which inputs, code, and data are used; freezing/sealing locks that content; a build refers to the program version produced from it; SHA is a cryptographic content digest rather than just checking a filename. Later results cannot be automatically transferred to an older build. |

<a id="address-status"></a>
### Address Formulas and Comparison Labels

First distinguish two things: CLOSED/TABLE describe an item's rule or table dependency; EXACT, VACUOUS, and the like describe a comparison or its scope. They cannot substitute for one another.

| Label | How to understand it on first encounter |
|---|---|
| CLOSED / CLOSED_FORMULA | The corresponding audit item has an explicit rule, with applicable objects and scope as declared by that item; this does not mean the formula is wired into the executor, nor does it automatically obtain native numeric acceptance. |
| TABLE | The item still depends on data from a given table; the table can work properly in measured instances, and this label does not mean "computation failed". |
| EXACT / 0 | The address-table comparison here is identical across the declared field, geometry, and element scope, with 0 mismatches; this is not a proof for all inputs or for the internal hardware structure. |
| VACUOUS | The compared object is an empty array with no non-empty elements to check; one cannot claim from this that a non-empty address rule has been verified. |
| NOT_PRESENT | This field is absent in the specified source; it cannot be understood as "the field contents are all zero". |
| OUT_OF_SCOPE | The object falls outside the declared scope of this comparison; neither pass nor fail is filled in on its behalf. |

"Held-out" refers to elements not used for fitting when deriving the rule and read for comparison only after the formula is frozen; it does not require that the corresponding shapes or metadata have never been seen before. Address-table equality, which table the actual executor reads, numeric-chain acceptance, and formal proof remain distinct questions.
